# Assessment Spec Harness — 공개 계획 v1.0

## 0. 이 문서의 목적

이 문서는 이 프로젝트를 포트폴리오 작품으로 공개하기 위한 정본(canonical)이자
살아있는 계획이다. `implementation_plan_assessment_harness_poc_v1.md`가 구현을
관장하는 것과 같은 방식으로 이 문서는 **공개 작업**을 관장한다. 즉 단일 진실
출처(single source of truth)이며, 버전이 관리되고, 작업이 진행됨에 따라
갱신된다. **이 계획은 프로젝트가 공개되는 순간에 완료된다** — 인벤토리를
마무리하고 미결정 사항(Open Decisions)을 닫는 것 *자체가* 공개다.

이 계획 자체도 공개 산출물이다(Owner 결정, 2026-05-29). 이는 공개가 어떻게
추론되었는지를 보여주며, 프로젝트의 핵심 프레이밍과도 일치한다 — **코드만이
아니라 결정과 과정을 전면에 내세운다.**

## 1. 공개 원칙 (타협 불가)

1. **과대 주장 금지.** 구현된 것 대 미결인 것을 어디서나 정직하게 명시한다.
   저장소 자체의 규율(검증 기록, "갭을 미래 작업으로 재구성하지 말 것")은
   공개 문서에도 동일하게 적용된다.
2. **코드보다 결정과 과정.** 차별화 요소는 *왜 코드가 지금의 모습인가* — 즉
   판단, 트레이드오프, 화해(reconciliation) — 이지 단순 LOC가 아니다.
3. **사실당 단일 진실 출처.** 각 사실(테스트 개수, 상태, 버전)은 정확히 하나의
   문서에만 존재하고, 나머지는 모두 링크한다. 중복은 우리가 명시적으로
   제거하려는 드리프트(drift) 메커니즘이다.
4. **감사(audit) 규율은 일급 자산이며, 숨기지 않고 보여준다.** 독립적인 검증
   기록과 계약 화해는 시니어 신호이므로 묻어두지 말고 드러내야 한다.
5. **영어 우선 + 한국어 미러.** 별도 파일(`*.md` EN, `*.ko.md` KO)로 두며,
   영어가 정본이다. 각 파일은 언어 전환 헤더를 포함한다:
   ```html
   <p align="center">
     <a href="./README.md"><img src="https://img.shields.io/badge/Language-EN-111111?style=for-the-badge" alt="English"></a>
     <a href="./README.ko.md"><img src="https://img.shields.io/badge/Language-KO-6B7280?style=for-the-badge" alt="한국어"></a>
   </p>
   <p align="center"><sub>Switch language / 언어 전환</sub></p>
   ```
6. **이 계획은 공개된다.** 메타 과정을 전시한다.

## 2. 대상 독자 및 프레이밍

- **주 공개 대상:** 채용 담당자 / 면접관(사람). 영어로 읽으며, 3–5분을 들인다.
  진입점은 `README.md`이다.
- **부 대상:** 프로젝트를 이어가는 AI 작업자 — 내부 운영 문서(`HANDOFF.md`,
  `AGENTS.md`, `CLAUDE.md`)가 이들을 지원한다.
- **프레이밍 목표:** *명시적 결정 근거, 정직한 범위, 검증 증거를 갖춘 시스템
  설계 PoC*로 제시한다 — "기능이 많은 프로젝트"가 아니다. 독자는 문제, 설계
  판단, 오늘 동작하는 것, 그리고 의도적으로 미룬 것을 이해한 채로 떠나야 한다.

## 4. 어떻게 / 순서 (작업 계획)

각 단계는 작고 자족적인 커밋이며 `work_log` 항목을 동반한다. 슬라이스 작업과
프레젠테이션 작업은 별도의 커밋으로 유지한다(확립된 관례).

- [ ] **Step 0 — 진실 패스(가장 먼저).** 공개 표면을 예쁘게 만들기 전에 먼저
      *정확하게* 만든다. README 계획 버전 v1.28 → v1.30; 선형적인 "Phase 1/2/3
      후" 표를 **영역 기반 상태 표**로 교체한다(작업은 선형적으로 진행되지
      않았다 — Phase 2 기반은 존재하나 Phase 1 수동 실행은 없으므로, 선형 표는
      적극적으로 오해를 유발한다); 다른 과대 주장이 있는지 점검한다.
- [ ] **Step 1 — 이중 언어 스캐폴드.** EN/KO 파일 쌍과 언어 전환 헤더를 쇼케이스
      문서 *및* 기술 문서(HANDOFF / AGENTS / CLAUDE; 구현 계획은 §7a에 따름)에
      대해 생성한다. README에 **Mermaid 아키텍처 다이어그램**을 임베드한다(별도
      아키텍처 문서를 대체).
- [ ] **Step 2 — 케이스 스터디 + 결정 비네트(핵심).** 기존 `work_log` 결정 +
      검증 평결에서 3–5개의 결정을 큐레이션하여 **무엇 / 왜 / 트레이드오프 /
      어떻게 검증했는가 / 어디서 확인하는가(링크)** 형태로 만든다.
- [ ] **Step 3 — 평가(측정).** 테스트/스모크 표를 **실제 `docker compose run`
      출력으로부터** 구축한다. 절대 옮겨 적지 않는다. 모든 수치는 재계산한다.
- [ ] **Step 4 — AGENTS / CLAUDE 보강.** 아직 존재하지 않는 에이전트 워크플로
      규칙을 추가한다. 기존 내용을 중복하거나 모순되게 하지 않는다.
- [ ] **Step 5 — 참조 정리 + 안전 스캔.** `LICENSE` 추가(Apache 2.0, §7.4);
      `daily_logs`/`verifications`에 대한 큐레이션된 인덱스 구축(§7.7); 작업
      트리 *및 히스토리* 전반에 대한 비밀/자격 증명 스캔(저장소는 있는 그대로
      공개되므로 히스토리도 노출된다); 깨진 링크 수정; 픽스처에 사적 데이터가
      없는지 확인.
- [ ] **Step 6 — Documentation Map.** "어떤 목적에는 어떤 문"인지 명확한 지도와
      함께 README를 모든 문서에 연결한다.
- [ ] **Step 6.5 — 모든 문서 동결 + 미러(§7b).** 개발과 공개 카피가 동결되면,
      이중 언어 미러를 한 번에 생성한다: 구현 계획의 전체 영어 미러, 이 공개
      계획의 `.ko` 미러, `HANDOFF.md` 미러, README EN/KO 전환, 그리고
      쇼케이스/문서 미러.
- [ ] **Step 7 — 가시성 전환(Owner, 수동).** Owner가 저장소 설명/토픽을
      설정하고 `entangelk/assessment_poc`를 공개로 전환한다; 이 계획은 바로
      붙여넣을 수 있는 메타데이터를 제공한다.

## 5. 강조할 결정 비네트 (후보, 3–5개로 큐레이션)

- [ ] **`validated` 과대 주장 → 단계화 모델 → 3방향 라우팅** (대표 사례). 한
      계약은 `validated`를 "모든 Rule 0 통과"로 정의했으나, 분류기는 스키마 +
      귀속(attribution) 검사만 거친 뒤 그것을 부여했다 — 댕글링 참조
      후보(dangling-reference candidate)가 평가에 도달할 수 있는 안전 갭. 독립
      검증으로 포착되었고, 모델을 단계화(`structurally_validated`)한 뒤 실패
      상태를 분할하여 해결했다. 원칙은 *"하류 분기가 갈라지는 만큼만, 그리고
      이름이 거짓이 될 만큼만 상태를 분할하라."*
- [ ] **`ai_judgement` 과도 엄격 가드** — 의미 판단 인용문은 문자 그대로의 부분
      문자열일 것을 강제하지 않는다; 그 경계와 이유.
- [ ] **합집합 기반 컴팩팅, 자동 수용 없음** — 가치 결정: 실행 간 불일치는
      검토를 위해 보존되며, 절대 조용히 병합되지 않는다.
- [ ] **`check` 대 `gate` 경계** — `check`는 외부적으로 절대 차단하지 않으며;
      `gate`만이 유일한 외부 통과/실패 평결이고, 필수 인간 검토 뒤에 놓인다.
- [ ] **에이전트가 소비 가능한 CLI 안정 코어** — 출력 계약은 사람이 아니라 AI
      호출자를 위해 설계되었다.

- [ ] 비밀/자격 증명 스캔이 깨끗하다(트리 + 히스토리).
- [ ] 이중 언어 패리티: EN과 KO가 동일한 사실을 진술한다.

## 7. 해결된 결정 (킥오프 Q&A, 2026-05-29 → v1.1)

1. **결정 기록 = 독립 `docs/decisions.md`** (+ `.ko`). 케이스 스터디 안의 한
   섹션은 비네트가 쌓이면 너무 길어질 것이다.
2. **이중 언어는 기술 문서까지 확장된다**, 쇼케이스만이 아니다. 각 문서는 언어
   전환 헤더를 가지며; EN 문서는 EN 문서로, KO는 KO로 링크한다. (대형 구현
   계획의 정확한 범위: §7a 참조.)
3. **별도 `architecture.md` 없음.** 대신 README에 **Mermaid 아키텍처
   다이어그램**(draw.io 스타일 비주얼)을 임베드하고 계획으로의 링크를 더한다.
4. **라이선스 = Apache 2.0.** 허용적(permissive): 고지 + 라이선스 유지와 특허
   허여(patent grant)를 조건으로 자유로운 사용/수정/배포; 저작권 소유자 =
   `entangelk`(Owner가 법적 이름으로 교체할 수 있음).
5. **저장소 메타데이터 + 가시성 전환 = Owner가 수동으로 수행**(이 환경에 `gh`
   없음). 이 계획은 Owner에게 바로 붙여넣을 수 있는 설명/토픽을 넘긴다.
6. **데모 대 결과 산출물: 보류.** Demo/Results 섹션을 예약해 두고, 터미널
   캐스트와 정적 외부 분석 결과 사이에서 나중에 결정한다.
7. **`docs/daily_logs/`와 `docs/verifications/` → 큐레이션된 인덱스**, 공개
   표면에 전체 원본을 두지 않는다(너무 길다). 짧은 인덱스가 주목할 만한 것들을
   링크한다.

인덱스를 통해 노출. 남은 미결 항목은 §7a로 이동했다(구현 계획의 이중 언어 범위,
이 계획의 `.ko` 미러, 저장소 메타데이터 문구).

### v1.0 (2026-05-29)

초기 공개 계획. 킥오프 Q&A에서 포착한 Owner 결정:
- **언어:** 영어 우선 + 한국어 미러를 별도 파일로, 각 파일에 언어 전환 헤더.
- **"공개"의 범위:** 기존 `entangelk/assessment_poc` 저장소를 정리하여 공개로
  전환(히스토리는 유지되며 결정 내러티브의 일부로 취급됨; 비밀 스캔 필요).
- **이 계획은 공개된다:** 공개 추론 자체를 보여주기 위한 포트폴리오 산출물로
  포함된다.
근거는 §1에 녹아 있다: 코드보다 결정/과정을 전면에, 사실당 단일 진실 출처, 감사
규율을 자산으로 전시, 공개/내부 문서 역할 분리, 평가 수치는 옮겨 적지 말고
측정할 것.
